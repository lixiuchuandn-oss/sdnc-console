# 权限管控 - 权限原子 需求设计（PRD）

## 1. 概述

权限原子（Action）是平台访问控制体系中的最小授权单元，对应“某一类资源在某一类操作上的能力”，通常与一个或一组后端 API 调用绑定。平台通过“权限原子 → 权限策略（Policy） → 角色（Role） → 用户/租户”的链路实现统一的细粒度访问控制。

本 PRD 重点定义：

- 权限原子的命名规范与分组模型。
- 权限原子与后端 API 的绑定方式。
- 权限原子列表页面（`/admin/access/actions`）的展示与交互。
- 权限原子在策略、角色与前后端鉴权中的使用方式。

范围说明：本 PRD 只聚焦“权限原子”本身，不展开策略管理与角色管理的完整细节，仅描述其关联关系。

## 2. 背景与目标

### 2.1 背景

- 现有系统已经具备 RBAC 能力，前端路由和部分后端接口使用字符串型的 Action 标识进行权限判断。
- 旧文档中已经抽象出“权限原子 / 权限策略 / 角色”的三级模型，但缺乏：
  - 对 Action 命名规范的统一约定。
  - 对“哪些 API 映射到哪些 Action”的可视化能力。
  - 对“未落地到 API 的策划中 Action”的显式管理能力。
- 多云管理、租户管理、安全域管理等模块快速演进，需要一个统一可浏览的“功能点目录”，以支撑权限策划、三权分立角色设计与审计。

### 2.2 目标

- 提供一个统一的权限原子目录，覆盖 CNMC/SDNCC/CNSOC 等平台的主要功能点。
- 建立规范的 Action 命名体系，避免各模块各自发明字符串。
- 自动从后端路由扫描已绑定的 API，标记 Action 的“落地状态”（已绑定/策划）。
- 为“权限策略 PRD”“角色管理 PRD”“租户子用户授权”等提供基础能力。

## 3. 核心概念

### 3.1 权限原子（Action）

- 定义：最小权限单元，代表“某资源集合上的某种操作能力”。
- 形式：`<资源前缀>.<子域>...:<动词>`，例如：
  - `clouds.instances:read`：查看云主机列表和详情。
  - `clouds.instances:write`：创建、修改、删除云主机。
  - `tenants.leased-lines.list:read`：查看租户专线列表与详情。
- 特性：
  - 粒度细：通常对应一类 API（GET/POST/PUT/DELETE）组合，而不是粗粒度模块。
  - 数量多：预期可达数百到上千。
  - 直接用于前端路由、后端接口鉴权。

### 3.2 权限策略（Policy）

- 定义：一组权限原子的集合，可附带条件（租户、组织、资源标签等）的高级授权单元。
- 示例：`云资源-只读策略`、`租户管理-写入策略`。
- 说明：策略管理由独立 PRD 定义，本 PRD 仅要求策略能引用 Action 列表。

### 3.3 角色（Role）

- 定义：权限载体与虚拟身份，承载一组策略或一组权限原子。
- 示例：`三权-审计员`、`三权-运维操作员`、`三权-策略管理员`。
- 说明：角色管理由独立 PRD 定义，本 PRD 只要求角色能引用 Action 集合。

### 3.4 平台（Platform）与分组（Group）

- 平台（Platform）：顶级产品域，用于区分权限归属：
  - `CNMC`：多云管理。
  - `SDNCC`：SDN 管理。
  - `CNSOC`：AI SOC 中心。
- 分组（Group）：侧边栏维度的功能分组，如：
  - `资源控制台`、`租户管理`、`售卖管理`、`权限管控`、`安全管理面`、`跨地域互联`、`流量编排`、`安全运营` 等。
- 权限原子通过其资源前缀与统一功能目录映射到对应的平台和分组，用于：
  - 在“权限原子列表”中按平台/分组筛选。
  - 在“系统策略自动生成”时按分组聚合 read/write。

## 4. 用户与权限

- 超级管理员（System Super Admin）：
  - 可查看所有平台的全部权限原子。
  - 可查看 Action 与实际 API 绑定情况，用于审计。
- 系统管理员（具有权限管控模块访问权限的管理员）：
  - 可查看所有 Action，但仅限查看，不直接修改 Action 定义。
  - 在策略/角色管理中使用这些 Action。
- 租户管理员/租户操作员：
  - 一般不直接访问“权限原子”列表，而是通过预置策略与角色获取权限。
  - 如后续扩展“租户侧自定义权限策略”，可以选择开放只读查看能力。

初版：权限原子列表仅对具有 `access.actions:read` 能力的系统角色开放；只有超级管理员可修改后台路由或 RouteSpec，从而间接调整权限原子。

## 5. 功能范围

### 5.1 权限原子列表页

路由：`/admin/access/actions`

- 主要目的：
  - 以树形加列表视图展示全量权限原子。
  - 显示每个权限原子是否已有后端 API 绑定。
  - 支持按平台、分组、关键字等快速检索。
- 视图结构：
  - 左侧：基于“平台 → 分组 → 功能 → Action”的树形导航。
  - 右侧：表格列表，展示权限原子的核心属性。
- 列表字段：
  - 权限原子：Action 字符串，例如 `clouds.instances:read`。
  - 功能：对应的业务功能名，例如“云主机”“租户专线列表”等。
  - 分组：例如“资源控制台”“租户管理”“权限管控”等。
  - 描述：根据 Action 自动生成的中文描述，例如“查看云主机列表与详情”“创建、修改、删除租户专线记录”。
  - 状态：
    - `已绑定`：已扫描到至少一个实际 API 路由绑定到该 Action。
    - `策划`：目前仅存在于前端路由或功能策划中，尚未有实际 API 绑定。
- 筛选条件：
  - 顶级目录（平台）：全部 / CNMC / SDNCC / CNSOC。
  - 分组：全部 / 各业务分组。
  - 状态：全部 / 已绑定。
  - 关键字：对 Action 字符串模糊搜索。

### 5.2 权限原子与 API 绑定视图

- 在列表中展开某一行时，可查看该权限原子绑定的 API 列表：
  - 功能名：例如“查询资源池列表”“创建资源池记录”等，根据 HTTP 方法和路径推导。
  - 方法：GET / POST / PUT / PATCH / DELETE。
  - 路径：后端 API 的 URL 路径，例如 `/api/clouds`。
  - 文件：后端路由定义所在文件路径，用于定位问题。
  - 用途：简要用途描述，例如“读取资源或信息”“创建或触发动作”等。
- 用途：
  - 协助产品与后端确认 Action 与接口的覆盖关系。
  - 在审计时追踪某个角色具备的权限到底能调用哪些 API。

### 5.3 与策略管理和角色管理的联动

- 系统策略：
  - 系统自动基于分组和读写动词生成系统策略，例如：
    - `资源控制台-全部权限`：包含“资源控制台”分组下所有 read/write Action。
    - `资源控制台-只读权限`：仅包含 read Action。
    - `资源控制台-写入权限`：仅包含 write Action。
  - 这些系统策略在策略管理页面中以只读形式展示，用于快速为角色赋权。
- 三权分立默认角色：
  - 基于全量 Action 集合，系统自动创建：
    - `三权-审计员`：所有分组的只读 Action。
    - `三权-运维操作员`：所有分组的只读加运维相关分组的写入 Action。
    - `三权-策略管理员`：所有分组的只读加管理分组的写入 Action。
  - 此逻辑依赖 Action 的分组信息，因此要求权限原子分组准确。

### 5.4 权限原子在前端路由与后端接口中的使用

- 前端路由：
  - 每个管理端路由定义所需权限原子，例如：
    - 页面访问：`requiredActions.page`。
    - 只读操作：`requiredActions.read`。
    - 写入操作：`requiredActions.write`。
  - 管理端布局根据当前用户权限数组判断是否展示路由和按钮。
- 后端接口：
  - 某些接口根据请求路径与 HTTP 方法映射到 Action，并进行权限判断：
    - 读操作：映射为 `xxx:read`。
    - 写操作：映射为 `xxx:write`。
  - 要求：
    - 后端对外接口的 Action 映射规则与权限原子命名规范保持一致。
    - 所有需要鉴权的管理类接口在路由设计阶段确定对应的 Action。

## 6. 业务流程

### 6.1 权限原子全量生成与展示

1. 产品或前端在路由配置中为各页面、功能定义 `requiredActions`。
2. 后端通过统一路由扫描逻辑，从路由目录中提取需要权限控制的接口，按路径与方法映射为 Action：
   - 识别资源域前缀，如 `clouds.instances`、`tenants.leased-lines.list` 等。
   - 将 GET/HEAD 归为 `:read`，其他方法归为 `:write`。
3. 管理端“权限原子列表”页面：
   - 将前端路由中声明的 Action 与后端扫描到的 Action 合并去重。
   - 对于在扫描结果中出现的 Action，标记为 `已绑定` 并附带 API 列表。
   - 仅在前端存在而后端暂未绑定的 Action，标记为 `策划`。
4. 同一 Action 被多个 API 使用时，在展开行中列出全部 API。

### 6.2 新功能接入权限体系

1. 在设计新功能时，产品与后端确定资源前缀与读写边界：
   - 例如“Harvester 命名空间管理”可采用 `clouds.namespaces:read/write`。
2. 前端路由在新页面、按钮处使用该 Action：
   - 页面访问：`access.actions` 等。
3. 后端为新接口配置 Action 映射：
   - 在路由扫描逻辑或中间件中按照同一命名规范生成对应 Action。
4. 发布后：
   - “权限原子列表”中出现新的 Action，并自动标记为 `已绑定`。
   - 策略和角色页面可以将该 Action 纳入策略和角色的权限范围。

## 7. 命名规范与数据模型

### 7.1 Action 命名规范

- 基本结构：`资源前缀[.子域...]:动词`。
- 资源前缀：
  - 采用小写单词加点号分隔，通常与后端路由模块对应。
  - 示例：
    - `clouds.instances`、`clouds.vpcs`、`clouds.security-groups`。
    - `tenants.leased-lines.list`、`tenants.leased-lines.manage`。
    - `security-domain` 相关前缀按 SDN 模块设计约定。
- 动词：
  - 当前阶段仅使用 `read` 和 `write` 两种：
    - `read`：查看、查询、下载类操作。
    - `write`：创建、修改、删除、触发任务等对资源有影响的操作。
  - 后续如需扩展其他动词，需在权限管控总体 PRD 中统一设计。

### 7.2 权限原子数据结构（逻辑模型）

- ActionItem：
  - `action`: string；Action 标识。
  - `platform`: string；所属平台。
  - `group`: string；所属分组。
  - `feature`: string；功能名。
  - `description`: string；中文描述，自动推导，支持后续手工覆盖。
  - `bound`: boolean；是否已绑定到至少一个后端 API。
  - `apis`: ApiItem[]；绑定的 API 明细。
- ApiItem：
  - `method`: string；HTTP 方法。
  - `path`: string；API 路径。
  - `file`: string；后端路由定义文件路径。

初版实现中这些字段主要由前端聚合与后端扫描结果组合而成，无需持久化到数据库；后续如需审计报表，可考虑落表。

## 8. 非功能需求

- 一致性：
  - 前端路由使用的 Action 与后端扫描生成的 Action 必须遵循统一命名规范。
  - 多模块共用资源前缀时，应在设计阶段评审，避免歧义。
- 性能：
  - 权限原子列表加载时间在常规规模下应控制在 3 秒内。
  - 路由扫描应在系统启动或定时任务中完成，不阻塞正常 API 请求。
- 可扩展性：
  - 支持后续增加更多平台与分组，无需修改已有 Action 命名。
  - 预留在策略层引入条件（如租户、组织、标签）的空间。

## 9. 验收要点

- 基础展示：
  - 能在“权限原子”页面看到全部 Action 列表。
  - 能按平台、分组、状态、关键字筛选 Action。
- 绑定状态：
  - 已在后端实现鉴权的接口，对应的 Action 在列表中显示为 `已绑定`，展开时能看到至少一个 API 记录。
  - 仅存在于路由配置且尚未实现 API 的 Action 显示为 `策划`。
- 命名规范：
  - 新接入模块的 Action 命名符合“资源前缀:read/write”的规范。
- 联动：
  - 系统策略能基于 Action 列表按分组自动生成。
  - 默认“三权角色”能基于 Action 列表自动生成，并在角色管理页中可见。
- 权限控制：
  - 未拥有 `access.actions:read` 能力的用户访问 `/admin/access/actions` 时，前端路由隐藏入口，后端访问接口返回权限不足。
