# 全栈算力运营平台研发演进计划 (Development Plan)

## 1. 背景与目标
基于现有的 `Compute.Tower` 多云基础设施管理平台（IaaS），通过四个阶段的迭代，构建满足高校/科研机构需求的“全栈算力运营平台”。核心目标是补全**运营计费**、**AI/HPC 作业环境**、**统一服务门户**及**生态集成**能力。

---

## 2. 阶段一：商业化运营基石 (计费与产品化)
**目标**：将底层的“资源”转化为可售卖的“商品”，实现精细化的成本回收与控制。

### 2.1 核心功能模块
1.  **产品定义 (Product Catalog)**
    *   **需求**：管理员配置主机/GPU单价，定义资源规格（如“A100计算卡套餐”）。
    *   **实现**：新增 `Product` 和 `PricePolicy` 实体。支持按时、按量、包年包月多种计费模式。
2.  **账户与充值 (Billing System)**
    *   **需求**：支持用户/课题组账户充值、余额管理、欠费停机。
    *   **实现**：
        *   新增 `Account` (余额表) 和 `Transaction` (流水表)。
        *   开发“充值接口” (支持管理员后台充值或模拟支付网关)。
3.  **计量与扣费引擎 (Metering & Charging)**
    *   **需求**：实时或准实时计算资源消耗，生成账单。
    *   **实现**：
        *   后端定时任务 (Cron Job) 扫描活跃实例。
        *   基于 `UsageRecord` 生成每日/每月账单 (`Invoice`)。
4.  **配额管理 (Quota V2)**
    *   **需求**：基于“金额”或“机时”的配额控制，支持在线申请扩容。

### 2.2 技术落地建议
*   **Backend**: 在 `backend/src/entities` 下新增 `billing/` 目录，通过 `typeorm` 管理计费相关表结构。
*   **Frontend**: 在 `frontend/src/pages/Billing` 下开发“费用中心”，展示余额、充值记录和消费明细图表。

---

## 3. 阶段二：AI/HPC 算力服务 (PaaS 层构建)
**目标**：屏蔽底层基础设施差异，为科研人员提供开箱即用的开发与计算环境。

### 3.1 核心功能模块
1.  **交互式开发环境 (Interactive Environment)**
    *   **需求**：提供 JupyterLab、VSCode Server 等在线 IDE。
    *   **实现**：
        *   集成 **JupyterHub** 或直接利用 K8s/Docker API 启动带有 Jupyter 的容器。
        *   利用现有的 `ws/ssh.ts` 扩展 Web Terminal 功能。
2.  **应用/镜像商店 (App Store)**
    *   **需求**：预置 PyTorch, TensorFlow, CUDA 等深度学习环境。
    *   **实现**：
        *   建立 `ImageRegistry`，管理经过验证的 Docker 镜像或 VM 模板。
        *   前端提供“一键部署”向导，自动配置驱动和环境变量。
3.  **作业提交与调度 (Job Scheduling)**
    *   **需求**：多卡并行训练，任务自动排队与运行。
    *   **实现**：
        *   开发简易调度器或对接 Slurm/K8s。
        *   支持“离线作业”模式：提交脚本 -> 排队 -> 执行 -> 结果回传。
4.  **弹性伸缩 (Auto-scaling)**
    *   **需求**：根据负载自动增减实例。
    *   **实现**：基于 `Monitor` 数据，通过 `ScalePolicy` 自动触发资源创建/销毁 API。

### 3.2 技术落地建议
*   **Backend**: 新增 `services/jobScheduler.ts`，处理任务队列状态机。
*   **Integration**: 研究 Harvester/K8s 的 CRD 集成，实现更轻量级的容器化算力交付。

---

## 4. 阶段三：统一门户与生态融合 (用户体验)
**目标**：打造面向最终用户的“服务大厅”，并融入学校现有的 IT 生态。

### 4.1 核心功能模块
1.  **服务门户首页 (Service Portal)**
    *   **需求**：区分“管理后台”与“用户前台”。前台展示资源概览、快捷入口、公告通知。
    *   **实现**：重构 `frontend/src/layouts`，增加 `UserLayout`，设计现代化的 Dashboard。
2.  **统一身份认证 (SSO)**
    *   **需求**：单点登录，对接学校门户。
    *   **实现**：
        *   改造 `backend/src/routes/auth.ts`。
        *   引入 `passport.js` 或类似库，支持 CAS, LDAP, OAuth2 协议。
3.  **数据与网盘集成 (Data & Storage)**
    *   **需求**：挂载阿里云盘/百度网盘，方便数据集传输。
    *   **实现**：
        *   利用 `Rclone` 或云盘官方 SDK，将云盘挂载为本地文件系统或提供中间传输服务。
        *   开发 `DatasetManager`，支持数据集的上传、共享和挂载。
4.  **消息通知中心 (Notification)**
    *   **需求**：站内信、邮件通知（余额不足、作业完成）。
    *   **实现**：建立消息队列，支持多种触达渠道配置。

---

## 5. 阶段四：智能运维与数据洞察 (稳健性)
**目标**：提升平台的可观测性与自动化运维水平。

### 5.1 核心功能模块
1.  **集群健康巡检 (Health Check)**
    *   **需求**：自动筛选故障节点。
    *   **实现**：定期运行测试脚本（如 GPU 冒烟测试），异常节点自动标记为 `Unhealthy` 并告警。
2.  **运营数据大屏 (Analytics)**
    *   **需求**：展示 GPU 利用率趋势、活跃用户时段、资金流向。
    *   **实现**：基于 ECharts 构建多维度可视化报表，数据源可对接 Prometheus 或自建统计表。

## 7. 实施路线图 (Roadmap)

| 阶段 | 周期 (预估) | 重点交付物 | 备注 |
| :--- | :--- | :--- | :--- |
| **Phase 1** | Month 1-2 | 计费系统、充值接口、基础账单、产品定义 | 解决“怎么卖”的问题，优先级最高 |
