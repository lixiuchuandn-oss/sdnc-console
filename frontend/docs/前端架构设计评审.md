# 前端项目在干什么？——写给完全新手的一份说明

你好。如果你刚接触这个项目、看目录有点懵，**这份文档就是写给你的**。

你不用一次读完。建议顺序：**先看「0. 超短总结」→ 再看「1. 用生活例子理解」→ 需要查词时看「2. 小词典」**，其余章节当「字典」随时翻。

---

## 0. 超短总结（30 秒版）

- **这个项目的前端**：就是一个很大的网站后台界面，用 **React** 做页面，用 **TypeScript** 写代码（带类型，减少写错）。
- **整体评价**：**没有乱到要推倒重来**；文件夹怎么分、页面放哪，团队有一份专门说明（`frontend/src/STRUCTURE.md`），这是好事。
- **主要「小毛病」**（以后慢慢改就行）：
  1. **地址（路由）写了两套地方**，改的时候要小心别只改一处。
  2. **和后端对话的代码**有几份特别长的文件，以后越来越难改。
  3. **画拓扑图**用了两套名字很像的库，有点浪费、也容易晕。
- **你作为新手最需要记的**：新页面、新文件**放哪**，请优先看 **`STRUCTURE.md`**，不要自己发明一套放法。

## 1. 用生活例子理解：前端代码像一栋商场

想象 **商场**：

| 商场里的东西 | 在前端里大概对应什么 | 你可以把它理解成 |
|--------------|----------------------|------------------|
| 每一层楼卖不同大类 | `pages/cnmc`、`pages/sdncc` 等，外加导航上的 **租户管理（TENANTS）** | **不同大产品区**（多云管理、**租户管理**、SDN、安全运营、系统设置） |
| 某一层的某个专柜 | 比如 `pages/cnmc/clouds/Harvester` | **某一块业务**（比如 Harvester 这朵云） |
| 专柜里的展示柜、抽屉、小弹窗 | `sections`、`drawers`、`modals` | **页面里的大块、侧栏、弹窗** |
| 全商场都能用的洗手间、电梯 | `components`、`hooks`、`utils` | **很多页面共用的零件和工具** |
| 收银台统一对接仓库发货 | `services` 文件夹 | **统一跟后端服务器要数据** |

**一句话**：代码按「**大产品 → 小业务 → 页面里的块**」分层，就像商场按楼层和专柜分区，**找东西会容易很多**。

## 2. 小词典（看到陌生词可以回来查）

| 词 | 白话意思 |
|----|----------|
| **React** | 做网页界面很常用的一套工具；页面是一块一块「组件」拼起来的。 |
| **TypeScript** | 在 JavaScript 上加「类型」；写错属性名之类会更容易被编辑器提示。 |
| **路由 / URL** | 浏览器地址栏里 `/admin/...` 那种路径；决定用户打开哪个页面。 |
| **`App.tsx`** | 整个前端应用的「总开关」之一，里面挂了好多路由（哪个地址显示哪个页面）。 |
| **`RouteSpec`（在 `routes/RouteSpec.ts`）** | 一份「路由说明书」：除了地址，还写了菜单标题、图标、**需要什么权限才能看**等。 |
| **`services`** | 封装「访问后端接口」的代码；页面尽量通过这里要数据，而不是到处自己写请求。 |
| **`Context`** | 放一些**全站都要知道**的东西，例如：当前登录的是谁、有没有授权、主题亮暗。 |
| **懒加载（lazy）** | 用户点到某个页面时，**再下载**那一块的代码，让第一次打开网站快一点。 |
| **Harvester** | 项目里一种云/集群相关的大块功能，文件特别多，所以单独占了一大块文件夹。 |
| **TENANTS / 租户管理** | 和「多云管理（CNMC）」**并列**的一大块产品；菜单、权限里单独成平台。代码文件目前还在 `pages/cnmc/tenants/` 文件夹里，是**过渡期**放法，**不等于**它还属于 CNMC 产品线。 |

## 3. 文件夹那么多，我该怎么记？

### 3.1 你只要先记住这几样

1. **`frontend/src/pages/`**  
   绝大部分「能看见的页面」都在这里。  
   下面先按 **大产品** 分文件夹：`cnmc`（多云管理）、`sdncc`（SDN）、`cnsoc`（安全运营）、`settings`（系统设置）等。  
   **特别说明**：**租户管理**在菜单和权限里是**单独一个平台（叫 TENANTS）**，和 CNMC 平级；只是页面代码暂时还放在 `pages/cnmc/tenants/` 里，以后有可能再挪文件夹——**看菜单/看 `STRUCTURE.md` 里的平台说明，不要只看文件夹名字。**

2. **`frontend/src/components/`**  
   很多页面都会用到的**通用界面零件**（例如通用表格容器之类）。

3. **`frontend/src/services/`**  
   **跟后端说话**的代码（取列表、保存、删除等）。

4. **`frontend/src/routes/`**  
   和**菜单、面包屑、权限**强相关的一份「路由说明」（尤其是 `RouteSpec.ts`）。

5. **`frontend/src/STRUCTURE.md`**  
   **官方规定：新文件应该放哪。** 看不懂目录时，**先打开这个**。

### 3.2 为什么有时候「网址」和「文件夹名字」对不上？

这是**故意的**。  
例如：网址可能是 `/admin/paas/databases`，文件夹可能在 `pages/cnmc/paas/...`。  
只要代码里写清楚了「这个网址去加载哪个文件」，就没问题。文档里也说了：**不必**强求网址和文件夹一层一层完全一样。

### 3.3 为什么有的地方看起来「还没整理完」？

团队在文档里说了：**可以慢慢迁**。  
所以你会看到「理想样子」和「现在样子」有一点点并存——**正常**，不是说你来背锅；你只要**新写的代码尽量按 `STRUCTURE.md` 的新规矩放**就好。

## 4. 「两套路由」是什么意思？（稍微进阶一点）

### 4.1 用一句话说

现在相当于：

- **A 处**：在 `App.tsx` 里，手写了很多「哪个网址 → 哪个页面」。
- **B 处**：在 `RouteSpec.ts` 里，又写了一份「每个菜单项的网址、名字、权限」等。

**两套都要维护**，所以专家说「有同步成本」——白话就是：**改网址或加页面时，要记得两边都看看**，否则可能出现「菜单有、页面打不开」或「权限对不上」之类的问题。

### 4.2 这样设计有没有好处？

有。**B 处那份说明书**对做「左侧菜单、权限控制、面包屑」特别方便，所以**不是白写**，只是**对新手不够友好**（要记两个地方）。

### 4.3 你以后参与改路由时，记住一句

> **动了地址或菜单，多想一步：`App.tsx` 和 `RouteSpec` 要不要一起动？**

### 4.4 这算不算「不规范」？

**不算违反什么官方标准**，也**不等于架构错了**。

可以这么理解：

- **React Router 官方教程**里，常见写法是：路由 mostly 写在一两个文件里。你们 **A 处（`App.tsx`）** 就是这一类，**完全正常**。
- **B 处（`RouteSpec`）** 不是第二套路由引擎，而是一份**给菜单、权限、面包屑用的「说明书」**。很多大后台会把「能点的菜单」和「真正挂载的页面」分开描述，只是有的团队用数据库配菜单，有的用 JSON/TS 文件——你们用的是 **TS 文件**，也很常见。

所以更准确的说法是：**这是一种有取舍的工程方案**——

- **好处**：菜单、权限、标题、图标和「真实页面」解耦，改文案或权限不必去翻巨大的 JSX。
- **代价**：路径/新页面要在两处对上号，**人多、改得勤时**容易漏，所以要靠习惯和以后可选的自动检查来补。

只有在这类情况才可以说「不太理想、该重构」：**两边经常对不上、线上总出菜单点了白屏**，那才值得花力气合成「一份配置生成两种用途」。在没出大问题之前，**保持现状 + 改的时候多检查**也是合理选择。

## 5. 「和后端说话」的代码（services）怎么了？

### 5.1 好的地方

- 大部分请求会走统一入口（例如统一的地址前缀、登录 token），**不容易各写各的、乱成一团**。
- 已经按厂商或大块功能拆了一些文件（比如 Harvester、阿里云等），**大方向是对的**。

### 5.2 小毛病（你不用紧张，知道就行）

有的文件**特别长**（比如通用 `api.ts`、Harvester 相关接口文件）。  
就像**一本电话簿全写在一个本子上**——能查，但以后改起来、两个人同时改，**更容易打架**。

以后团队可能会把它**拆成多本小册子**（多个文件），功能不变，只是更好找。

## 6. 登录、授权、主题这些存在哪？

主要在 **`contexts/`** 里，例如：

- 当前用户是谁、有没有登录；
- 授权（License）里哪些功能能用；
- 设置里主题色、深色浅色等。

你可以把它想成：**全商场广播的信息**，很多柜台都要听，就放在一个地方，**不用每个页面各记一份**。

## 7. 画图库为什么说了两次？（拓扑、流程图）

项目里同时用了两套名字很像的东西：**老的 `react-flow-renderer` 和新的 `reactflow`**。  
白话：**同一种活，两套工具**，会带来：

- 安装包变大一点；
- 新人会问「我到底该用哪一个？」。

这是**技术债**，慢慢统一就好，**不是你初学时必须掌握的细节**。

## 8. 工具链：听不懂可以跳过

- 现在用的是比较经典的一套脚手架（**Create React App**，脚本里常叫 `react-scripts`）。  
  **白话**：像「出厂自带装修」的房子，省事，但以后想换更潮的装修（比如更快的打包工具）要另做计划。
- TypeScript 版本不是最新的，**能跑、能用**；升级一般是整个团队排期的事。

## 9. Harvester / Cloudmap 为什么看起来特别庞大？

因为业务本身多：虚拟机、网络、存储、容器、监控……  
所以文件夹里文件多，**不等于架构坏了**；更关键的是：**有没有按规矩放进对应的小专区**。

你作为新手：**不要一次啃完**；你负责哪一块，就只熟悉那一块路径 + 对应 `STRUCTURE.md` 里怎么说。
